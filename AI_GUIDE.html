关卡工作台 · AI 设计指南

给任何 AI / 智能体：读完这一页，你就知道工作台怎么读你的地图、怎么判定“合格”，以及怎样设计出一张能直接进工作台、经得起关卡评审的地图。 字段的逐项定义在后面的《AI 关卡设计输出规范》；本页讲怎么用、怎么做好。

0. 你的任务（产出合同）

  • 只输出一份 JSON：不要解释、不要 Markdown 代码块、不要前后缀、不要注释或尾逗号。
  • 格式是 AI_MAP_SPEC v1（"schemaVersion": 1）。
  • 合格 = 同时满足： 1. 结构校验 0 错误（错误会让工作台直接拒绝导入）； 2. 0 告警（告警能导入，但说明设计有问题：门太窄、路线擦墙、门没在墙上……）； 3. 通过本页第 8 节的设计质量清单（校验器查不出来的东西，比如节奏、职责、引导）。
  • 你写的 JSON 是唯一真相：工作台不会替你补数据、不会自动修坐标；你没写的东西就不存在。（导入框有一个“自动吸附修正”选项，默认关闭；评审拿到的就是你的原始输出。）

1. 工作台怎么运作

工作台是一个只读的静态网页：读入地图 JSON → 校验 → 画成 2D 平面图、3D 块面和压力曲线。它不写回任何文件，也不连接游戏引擎。

你的 JSON ──► 校验（页面与 tools/validate_ai_map.py 同一套规则）
                │ 有错误 → 拒绝导入，提示第一条
                ▼
           2D 平面（SVG）   3D 块面（three.js）   压力节奏曲线   详情面板

你写的每类数据在哪里被看到：

数据 2D 平面 3D 块面 其他
floors[] 楼层页签、右栏“地图说明”里的竖向分层 每层楼板的标高 单看某层时其他层淡显
rooms[] 彩色多边形 + 名称（code + short） 楼板 + 沿房间边自动生成的墙 压力曲线背景色带、详情

2. 坐标、单位与尺度

  • 单位：米。 平面坐标 [x, z]：x 越大越靠东（图上向右），z 越大越靠北（图上向上）。
  • 标高不写在点里，而是来自 floors[].elevation；只有路线的点可以写第三个值 [x, z, y]（绝对标高）。
  • meta.bounds 是整张图的外框，所有点都必须在框内（含边上）。建议外框比房间整体大 1–2 m。
  • 用整数或 0.5 m 网格画房间与门，相邻房间才好严丝合缝；不要写 13.333 这类数。
  • 玩家尺度在 meta.player（一般 radius 0.35、height 1.7）。下表是推荐尺寸，用玩家直径 D = 2×radius 换算：
元素 硬下限（校验器） 推荐
门宽 width ≥ D（否则告警） 普通 1.6–2 m，主线/带怪通过 2–4 m
走廊宽 — ≥ 3 m；主战斗走廊 4–6 m
路线离阻挡物件 ≥ radius（否则告警） ≥ 1 m，主线 ≥ 1.5 m
敌人离墙 在房间内即可 ≥ 1 m
战斗房间 — 短边 ≥ 8 m；Boss 房 ≥ 12×12 m
层高 height > 0 3–4.5 m

3. 设计流程（按这个顺序写）

  1. 先定意图：一句话概念、目标时长/主线长度、几场战斗、一个高潮。写进 meta.subtitle 和 meta.designNotes。
  2. 楼层：floors[] 按 elevation 从低到高排列。单层图只写一个 1F。
  3. 房间网格：先在纸面上用矩形排布。相邻房间共用边界时，两边的坐标必须完全相同（这样门能落在边上，3D 墙会合并成一段）。同层房间不要重叠（外框重叠也会告警，L 形房间请拆成两个矩形房间）。
  4. 门：每扇门是一条落在房间边上的线段，两个点都在那条边上；width 等于线段长度。房间之间要连通，就一定要有门。
  5. 主线（kind:"main"，只要一条）：从入口房间里出发，每次换房间都穿过门的中点附近，最后停在终点房间里。折线点按行进顺序。避开 solid 物件至少 1 m。
  6. 敌人：每个敌人的 center 在它的 roomId 多边形内（同层），离墙 ≥ 1 m；主线上的写 branch:"main"，支线上的写 "optional"。
  7. 物件：掩体、展台、柱子等。会挡路的写 solid:true，并给 height（米）；不会挡路的写 solid:false。
  8. 可选路线（optional / secret / exit）：从主线分叉，给回报（资源、精英、捷径）。
  9. 多层时：加 stairs[]（写 bottom），跨层路线的点写成 [x, z, y]。
  10. 自检：按第 7、8 节逐条过；能跑命令时运行校验器。

4. 节奏：工作台怎么算压力

工作台沿主线（若有 exit 路线则接在主线后面）每 1 m 取一个采样点，计算：

压力(采样点) = Σ  权重(敌人) × exp(−距离 / 5.5 m)      只算 branch:"main" 的敌人
权重：meta.pacing.weights[enemyType]，缺省按 tier：normal 1 / elite 3 / boss 6
休息段：压力 < 峰值 × 20% 且连续 ≥ 4 m

距离按平面计算；多层图的主线路点写有绝对标高时，每个采样点先用 ±0.65 米标高范围筛选敌人。optional 敌人不计入。敌人的层位和与主线的距离共同决定曲线形状。机关、解谜等非战斗压力可以写进各段备注。

好的曲线是锯齿上升：

  • 开局低压（教学/观察），第一个小峰用 1–3 个普通敌人；
  • 每个峰之后留一段休息（≥ 4 m 低压，最好是一个安静房间或景观点）；
  • 峰值逐渐升高，最高峰在后段（Boss / 精英房），高潮前一定有一段休息；
  • 不要从头到尾一条高平线，也不要把所有敌人堆在一个门口。

可用 meta.pacing 微调：{ "lambda": 5.5, "aggro": 8, "step": 1, "weights": { "melee": 1, "elite": 3, "boss": 6 } }（weights 的键是 enemyType）。

5. 多层地图

  • 每层一个 floors[] 项，elevation 可为负（地下）；同一层的房间不重叠，不同层可以上下重叠。
  • 楼梯：stairs[] 的 points 是矩形占地；fromFloorId/toFloorId 是两端楼层；bottom 写低端在哪一侧（N/S/E/W，N = z 大的一侧，E = x 大的一侧）。不写时 3D 只能推测朝向。
  • 楼梯占地要落在两端楼层都有房间的位置（起点层的房间里，并对着目标层的房间）。
  • 跨层路线：路线的 floorId 写出发层，经过楼梯的点写成 [x, z, y]：楼梯低端点用低层标高，高端点用高层标高，之后在新楼层上的点都带 y。
  • 敌人、门、物件都按所在楼层写 floorId，敌人必须在同层房间里。

6. 3D 怎么显示（写对字段，3D 才像样）

  • 墙：沿每个房间的边自动生成，高约 0.8×层高（上限 2.4 m）。露天庭院、广场、中庭写 "wallHeight": 0，就不会被围墙；需要矮墙/高墙时写具体米数。
  • 门：落在墙上的门会自动开洞——门不在边上，墙上就没有洞。
  • 物件高度：写 height 最准；不写时按 kind 估算（如 column/pier 3 m、altar 1.1 m、case/display 1 m、bench 0.45 m、sign 1.8 m，其他 0.8 m），且不超过层高。
  • 特殊物件 kind：floor-finish/floor-inlay = 贴地铺装（不挡路）；combat-space = 战斗留白虚线框；loot = 资源点；interaction = 交互点；extract = 撤离点（搜打撤地图请用它标每个出口，工作台的“撤离距离”图层据此计算到最近出口的步行距离；也可用 kind: "exit" 的路线终点）。
  • 颜色 color 用 #rrggbb；不写就用默认色。

8. 设计质量清单（校验器查不出，但评审会看）

  • [ ] 主线完整：从入口到终点连续，每次换房间都穿过门；不穿墙、不穿实心物件。
  • [ ] 每个房间有职责：写 beat（这里发生什么）或 role；没有“只是为了凑面积”的空房。
  • [ ] 先教后考：第一场战斗简单、空间宽；新敌人类型先单独出现，再混编。
  • [ ] 锯齿节奏：压力有起伏，峰后有休息，最高峰在后段，Boss 前有喘息。
  • [ ] 可选内容有回报：每条 optional/secret 路线终点有资源、精英或捷径，并在 note 里写明。
  • [ ] 没有意外的死胡同：每个房间至少一扇门；单入口房间要有存在理由（宝箱、密室）。
  • [ ] 能撤离（有出口的地图）：撤离点用 kind: "extract" 标出；工作台“撤离距离”图层里不应有灰色（到不了出口）的可走区域，跨层靠 stairs[] 连通。
  • [ ] 敌人位置合理：不贴墙、不堵门口正中、不在楼梯上；精英/Boss 房有活动空间（≥ 8 m 短边）。
  • [ ] 引导：主线方向上有地标（大物件、亮色房间、开阔视野），不靠墙硬挡。
  • [ ] 意图写清楚：meta.designNotes 2–5 条，说明结构、节奏、关键取舍；需要人确认的事写进 reviewNotes。
  • [ ] 数字干净：坐标用整数或 .5；门宽与线段长一致；ID 语义化（r_entry、d_court、e_boss）。

9. AI 最常犯的错

  1. 方向反了：把 z 当成向下（南）。记住：z 越大越北，图上越靠上。
  2. 门画在房间中间或只碰到一个房间：门必须在两个房间共用的那条边上。
  3. 房间互相压盖：为了做 L 形把两个矩形叠在一起 → 改成共边相接。
  4. 敌人在墙上/房间外：center 恰好落在边上时判定不稳定（可能被判为房间外），一律往里挪 ≥ 1 m。
  5. 路线穿过家具：主线画直线穿过祭台、展柜 → 加折点绕开。
  6. ID 重复：楼层 1F 和房间 1F 也算重复。
  7. 输出带了 Markdown 代码块或说明文字：工作台会解析失败。
  8. 坐标超出 bounds：最后加的物件/路线点常常越界。
  9. 多层地图忘了楼梯或标高：跨层却没有 stairs[]，路线点也没写 y。

10. 交付与迭代

  1. 输出 JSON，保存为 my-map.json。
  2. 校验（能运行命令时）：python tools/validate_ai_map.py my-map.json；每条问题都带 [code]，按第 7 节修。
  3. 在工作台导入：右上“导入 JSON”，或左侧“粘贴 AI 输出的 JSON”。左侧“校验”面板列出全部问题，点一条即定位；打开“问题标记”“通行宽度”图层看哪里出问题；切 3D 看墙、门洞、楼梯朝向是否合理。
  4. 有问题时，把校验输出原样交回 AI，只改出问题的部分，ID 保持不变。
  5. 评审意见：工作台的“批注”工具会导出带 reviewNotes 的地图 JSON（targetId 指对象，at: [x, z] 指位置）。收到这样的文件时，逐条处理 status: "open" 的批注，改完把该条 status 设为 "resolved"，其余内容与 ID 不变。

11. 机关、状态与连接

这些字段都是可选的。不写就是普通的静态地图；写了，任何 AI 都能读懂机关的空间和拓扑。运行逻辑（时序、计时、判定）不写进 JSON，留在引擎里。

baseHeight：悬空物件。 物件底面高出所属楼层标高多少米，0 = 落地；walkable 表示顶面能否站人（默认 false）。悬在深渊上方的物件不要求落在房间内，floorId 写它参照的那一层。baseHeight ≥ meta.player.height 的物件，即使 solid: true 也不挡地面通行。

{ "id": "o_lamp_1", "name": "悬挂信号灯 1", "kind": "relay-lamp", "floorId": "1F",
  "solid": false, "baseHeight": 2.5, "height": 1, "walkable": false,
  "points": [[14.1, 7.6], [14.9, 7.6], [14.9, 8.4], [14.1, 8.4]] }

states：物件有几种样子。 可移动卡位（每个卡位一个状态，带自己的 points）、开合的闸（打开时 present: false）、升降的桥。至少 2 个状态；状态 id 只需在本物件内唯一；initialState 省略则取 states[0]。物件本体的属性应与初始状态一致。带 states 的物件不参与 route-clearance 和距离场的阻挡。没有 links[] 指向它 → 玩家直接操作；有 → 由机关驱动。

{ "id": "o_gate", "name": "闸门", "kind": "gate", "floorId": "1F", "solid": true, "height": 4,
  "points": [[23.25, 5], [24.75, 5], [24.75, 7], [23.25, 7]],
  "initialState": "closed",
  "states": [ { "id": "closed", "name": "关闭" }, { "id": "open", "name": "打开", "present": false } ] }

links：谁触发谁。 顶层 links[]。from 是触发源（物件、敌人或房间的 ID；写房间 ID 配 trigger: "defeated" 表示该房间敌人全灭），to 是目标及其要进入的状态（带 states 的物件，或门的 open / closed）。一对多 = to 写多项；条件组合 = from 写多项加 require（all 默认 / any）。门可写 initial: "closed"，但要有连接把它设为 open。

{ "id": "lk_vault", "name": "双接收器开宝库门", "trigger": "activated", "require": "all",
  "from": ["o_receiver_1", "o_receiver_2"], "to": [{ "id": "d_vault", "state": "open" }] }

meta.proximity：离得够近就算相连。 用于连锁机关、信号中继、光环范围这类由位置决定的关系，不要逐条手写成连接。判定定义见规范“邻近规则（meta.proximity）”一节。想连通的一对，距离控制在 radius − 0.5 以内；想断开的一对，距离控制在 radius + 0.5 以上。不要把关键关系卡在临界值上。

"proximity": [ { "id": "signal", "name": "信号中继", "radius": 6,
  "kinds": ["relay-pole", "relay-crate", "relay-lamp", "relay-receiver"],
  "enemyTypes": ["drone"], "lineOfSight": true } ]

meta.kindLegend：自定义种类是什么。 kind 和 enemyType 是自由字符串。用了自定义种类，就在这里写 label（显示名）和 note（是什么、做什么）。

"kindLegend": { "relay-receiver": { "label": "接收器", "note": "收到信号后保持激活。" } }

openEdges：房间某条边不砌墙。 表达“三面有墙、一面临崖”。第 i 条边 = points[i] → points[(i+1) % n]，从 0 起。它只表示本房间不为这条边砌墙；同层另一个房间与它共用这条边且那边有墙时，墙仍会由对方砌出。

{ "id": "r_start", "name": "起始殿", "kind": "room", "status": "planned", "floorId": "1F",
  "openEdges": [1], "points": [[2, 2], [12, 2], [12, 14], [2, 14]] }

12. 进 UE 白盒（草案）

草案：待 UE 试搭验证后修订。

确定性导入工具链（推荐，防引擎内幻觉）： - 先在工作台点页头 「导出 ▾ → UE 白盒包」（或跑 python tools/export_ue_whitebox.py <map.json> --auto-snap），直接导出已按本节展开好的 *-ue-whitebox.json（含厘米坐标、wallRuns / wallSpans 墙段、门洞、门楣、楼梯踏步、expectedCounts 与 preflight）。 - 在 UE5 Editor 中直接运行固定脚本 tools/ue_import_whitebox.py 导入该构建包（真美术替换可挂 tools/ue_asset_mapping.sample.json 同格式对照表补偿 Pivot 与碰撞），再用 tools/ue_verify_whitebox.py 自动执行 3.10 核对；不要让 AI 在 UE 里现场重算几何与坐标。

给在 UE 里搭白盒的 AI：只看 JSON 和本节。JSON 里没有的东西不要搭；JSON 里有的东西一件不能少。

3.1 坐标映射

工作台坐标：x 向东，z 向北，标高 y 向上，单位米。UE：X 向前，Y 向右，Z 向上，单位厘米。两者都是左手系，映射不需要镜像：

UE 来自 JSON 换算
X z（北） X = z × 100
Y x（东） Y = x × 100
Z 标高 Z = (floors[].elevation + 额外高度) × 100
  • JSON 的 (0, 0)、标高 0 对应 UE 世界原点，不加偏移。
  • 朝向：北 = +X = Yaw 0°；东 = +Y = Yaw 90°。
  • 在 UE 顶视图里（+X 朝上、+Y 朝右）看到的应与工作台 2D 平面图一致：北在上、东在右。

3.2 楼板

  • 每个房间一块楼板：按 points 多边形，顶面在该层 elevation，向下厚 0.2 m。
  • 轴对齐矩形用缩放的立方体；其他多边形按多边形拉伸生成。做不到时停下报告，不要用外接矩形代替。
  • 楼梯开洞：某条楼梯的占地落在它上端楼层的某个房间内时，该房间的楼板在楼梯占地范围内开洞。

3.3 墙

对每一层分别执行，算法与工作台 map-geometry.js 的 wallRuns() / wallSpans() 一致：

  1. 收集边：遍历该层每个房间的每条边。跳过：墙高为 0 的房间的所有边；openEdges 列出的边；长度 < 0.15 m 的边。
  2. 墙高：rooms[].wallHeight；没写则取该层 floors[].height。（工作台预览为了看清内部，把缺省墙高压到层高 × 0.8 且不超过 2.4 m；UE 里用整层高。）
  3. 归线：把每条边归到它所在的直线上。直线用方向角（归一到 [0, π)，保留 3 位小数）和到原点的有向偏移（保留 2 位小数）标识。
  4. 合并：同一直线上的边按起点排序，首尾相接或间隙 ≤ 0.05 m 的并成一段，墙高取其中最大值。两个房间共用的边因此只砌一次。
  5. 开门洞：对每段墙，找出两个端点到该直线的距离都 ≤ 0.35 m 的门。洞沿墙的范围取门线段的投影；若投影比 width 短，则以投影中点为中心取 width 宽。切完后长度 ≤ 0.1 m 的残段丢弃。
  6. 砌墙：每个剩余墙段是一个盒体，厚 0.2 m、以直线为中心，底在该层 elevation，高为墙高。
  7. 门楣：门洞净高（见 3.5）低于墙高时，洞口上方补一块同厚的墙，从净高到墙顶。

3.4 门

  • 门洞由 3.3 第 5 步在墙上开出。每扇门另放一个不带碰撞的标记 Actor，位置在门线段中点、该层 elevation。
  • initial: "closed" 的门：洞口处放一块带碰撞的门板占位体（厚 0.2 m，宽 = width，高 = 门洞净高），作为该门的 closed 状态。门的 open 状态 = 门板隐藏且关闭碰撞。

3.6 物件

  • 每个物件一个 Actor：按 points 拉伸，底面和高度按 3.5。
  • 碰撞：solid: true 或 walkable: true → 阻挡；其余无碰撞。
  • 颜色：color 写了就用它，没写用该类型的默认色。同色共用一个材质实例，都来自同一个只有"基础色"参数的白盒母材质。

3.7 楼梯

  • 高差 Δh = 两端楼层标高之差。踏步数 N = clamp(round(Δh / 0.18), 3, 20)，与工作台一致。
  • bottom 指明低端在占地矩形的哪一侧（N = z 大的一侧 = UE +X；E = x 大的一侧 = UE +Y）。踏步从低端向对侧等分排列，每级高 Δh / N。
  • 每级是一个从低端楼层标高砌到该级顶面的实心盒体，带碰撞。
  • 没写 bottom：停下报告，不要猜。

3.8 状态与连接在白盒阶段怎么表示

白盒阶段只做占位体、标签和标记，不实现机关逻辑。理由：机关逻辑属于各项目的玩法代码，由不同的 AI 各写一套简易蓝图，结果不可能一致；而占位体和标记是可以逐项核对的。

  • 状态：带 states 的物件，每个状态搭一个 Actor，命名 <物件 id>__<状态 id>。初始状态可见、按该状态的 solid 设碰撞；其余状态隐藏并关闭碰撞。present: false 的状态搭一个不带网格的空 Actor 占位，保证数量对得上。
  • 连接：每条 links[] 放一个空 Actor，命名 link__<连接 id>，位置取第一个触发源；把 from、to、require、trigger 写进它的标签（Tags）。
  • 邻近规则：不搭任何东西。它是位置的函数，由玩法代码在运行时计算。
  • 标签：每个物件上方放一个朝向相机的文字标签，内容为 name；带状态的再加一行当前状态名。

项目可以另备一张"kind → 玩法类"的对照表，把占位体换成真正的玩法 Actor。对照表属于项目，不进 JSON，也不进本指南。没有对照的 kind 一律用占位体。

3.10 搭完后的自检清单

逐项写进报告，每项给出数字或文件，不写"已确认"。

  1. 数量：房间、门、物件（按状态展开后的 Actor 数）、敌人、楼梯、水面、路线、连接，各自的 Actor 数与 JSON 一致。逐类列出"JSON 数 / UE 数"。
  2. 墙段数：列出每层的墙段数和门洞数。
  3. 坐标抽查：至少抽 5 个实体，且须包含一个悬空物件、一个带状态的物件、一扇门、最高层和最低层各一个。列出"JSON 坐标 → 换算结果 → UE 实际位置"，误差 ≤ 1 cm。
  4. 朝向：UE 顶视图里北在上、东在右；任一楼梯的低端在 bottom 指明的一侧。
  5. 边界：所有 Actor 的包围盒都在 meta.bounds 换算后的范围内（墙厚和楼板厚允许超出 0.2 m）。
  6. 叠图：正交俯视截图，画面范围对齐 meta.bounds、北在上；与工作台"平面图"画法导出的同范围图片叠加比对，墙、门洞、物件位置应重合。两张图都附上。
  7. 状态：每个带状态的物件，初始状态可见且碰撞正确，其余状态隐藏且无碰撞。
  8. 通行：从主线起点沿主线走一遍（或逐段做碰撞扫描），列出被挡住的位置。初始关闭的门和初始挡路的状态物件挡住属于正常，其余都是问题。
  9. 邻近核对（地图有 meta.proximity 时）：按规范的'邻近规则（meta.proximity）'一节的判定定义，用 UE 里的实际位置算出初始状态下连通的节点对，与工作台'邻近连线'图层在同一张图上显示的结果比对。
